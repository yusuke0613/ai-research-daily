### OpenAI、GPT-6 Astra を公開 —— 争点はスコアではなく「ハーネス」
**何が起きた**: 9月3日(米国時間)にリリース。価格は入力$10・出力$50 per Mtok で、前世代の GPT-5.6 Sol($4/$20)の2.5倍。提供は Daybreak プログラム参加企業が先行し、ChatGPT Plus / Pro / Business / Enterprise、API、AWS が数日中に続く。公表値では OSWorld 72.6%、サイバー攻撃検証ベンチ ExploitBench(報道により ExploitGym 表記の揺れあり)で100%、サイバー系ジェイルブレイク評価での拒否率91.5%(Sol は59%)。サイバー能力は「Critical」評価。Greg Brockman 氏は会見を "Welcome to the AGI era" で締めくくった。最大の話題は ARC-AGI-3 で、ARC Prize 側の計測では**標準ハーネスで62.7%、プロバイダアダプタ(OpenAIのResponses APIによる独自コンテキスト管理・カスタム圧縮)で99.9%**。François Chollet 氏は標準66% / 連続会話ハーネスでほぼ100%、コストは1ゲームあたり約$360と述べている。プロバイダアダプタ側は両ハーネスが解けた167ペアで**約3.66倍高速・総トークン49%減**。ARC Prize は今後リーダーボードで両ハーネスの結果を併記する方針を表明した。開発側では Codex 0.153.1 が「既定設定を変えずに GPT-6-Astra をAPI経由で設定できる」対応を同日入れている。
**なぜ重要**: 同じモデル・同じ問題で、コンテキスト管理の実装を変えるだけでスコアが37ポイント動いた。これは「モデルの性能」と「ハーネス(文脈の運び方)の性能」が分離できないことをベンチマーク運営者自身が認めたということで、モデル選定の判断材料としてのベンチマーク単独値の意味が一段軽くなる。
**自分・社内への影響**: 他社比較の資料でスコアを引用するとき、ハーネス条件を併記しないと数字が独り歩きする。自社評価も「モデルを変えた効果」と「文脈の渡し方を変えた効果」を分けて測る設計にしておきたい。価格は2.5倍なので、Sol からの乗り換えは効率改善の実測が出てからで遅くない。

### Claude Code v2.1.259 —— MCP管理設定に破壊的変更、管理者は要確認
**何が起きた**: 組織がHTTP/SSE型のMCPサーバーを全ユーザーへ配布できる管理設定 `managedMcpServers` が追加された(コマンド実行型のエントリはスキップされる)。あわせて `allowedMcpServers` の適用範囲が**「ユーザーが自分で追加したサーバーのみを制御する」**に変更され、これまで許可リストで除外していた `managed-mcp.json` 由来のサーバーがアップグレード後は読み込まれるようになる。除外を続けたい場合は `deniedMcpServers` への移行が必要。もう一つ挙動が変わったのが管理設定ファイルの解析失敗時で、従来は黙って無効化されていたものが、今後は**起動そのものを拒否して原因ファイルを名指しする**。無人実行向けには `--permission-prompts none`(確認が要る操作を自動的に拒否し、権限モードの判断は生かす)が追加。セキュリティ修正では、Bash の `Read()` 拒否ルールがオプション値(`--ignore-revs-file=.env`、`-f.env`、`@file`)や `git diff`/`git grep` のファイル指定、`cd DIR && cat FILE` の複合コマンドに効いていなかった問題が塞がれた。
**なぜ重要**: 「静かに効いていなかった管理設定」を潰す方向の変更が続いている。前バージョンの権限ルール修正と同じ流れで、これまで効いているつもりだった設定が実は素通りしていた可能性を示唆する。
**自分・社内への影響**: 管理配布を使っている場合、アップグレード前に `allowedMcpServers` の棚卸しが必要。意図せずMCPサーバーが有効化される方向の変更なので、後回しにしにくい。配布中のJSON/plist/レジストリ値がパースできるかも事前確認しておく(失敗すると起動しなくなる)。CI・Routineなどヘッドレス運用は `--permission-prompts none` の採用を検討する。

## 今日の基礎

### ツール使用(Function Calling): エージェントの手足

**一言でいうと**: Function Calling は、LLMに**注文票の書き方だけを教える**仕組みです。料理人(LLM)は自分でコンロを触れません。代わりに「この伝票フォーマットで注文を書いてくれ」と渡しておくと、必要になったとき伝票を書いて出してくる。実際に火を使うのはホール係(あなたのプログラム)で、出来上がった料理を伝票の返事として料理人に戻す。LLMは一度も厨房機器に触れていません。

**仕組みの要点**: サイクルは3手です。①**ツール定義**: 呼び出し可能な関数の名前・説明・引数スキーマ(JSON Schema)をリクエストに含めて渡す。説明文はLLMが読む唯一の仕様書なので、「いつ使うか」を書くのが精度を決めます。②**呼び出し**: LLMは通常のテキストの代わりに「このツールを、この引数で呼びたい」という構造化された出力を返す。これは**要求であって実行ではない**——ここが最重要点で、LLMはネットワークにもファイルにも触っていません。③**結果返却**: あなたのコードが実際に関数を実行し、その戻り値を「ツール結果」として会話履歴に追加して、もう一度LLMを呼ぶ。LLMは結果を読んで、答えを返すか次のツールを要求する。この②③の往復をループで回し続ける装置がエージェントです。ツールが1つも要求されなくなった時点でループが終わる。

**実務でどう効くか**: 実行が自分のコード側にあるという構造は、そのまま**権限設計の置き場所**になります。認証・入力検証・レート制限・監査ログは全部③の手前に書ける。LLMが「本番DBを削除するツールを呼びたい」と言ってきても、実行するかを決めるのはあなたです。設計の勘所は3つ。ツールは粒度を粗くしすぎない(引数が10個あるツールは呼び間違えます)、説明文に「使わない条件」も書く、エラーは例外で落とさず「失敗した理由」を文字列でLLMに返す——最後の1つが特に効きます。理由が返れば、LLMは引数を直して自分で再挑戦できるからです。MCPはこのツール定義の受け渡しを標準化したもので、土台はここで説明した3手のサイクルと同じです。

## 社内導入メモ
今日は「冗長化のつもりが冗長化になっていなかった」という材料が2つ重なった。1つは3社同時障害で、モデルプロバイダを分散しても基盤クラウド(Azure・Cloudflare)が共通なら単一障害点は残るという実例。マルチモデル構成を可用性の根拠として説明している資料があるなら、「プロバイダ分散」と「インフラ分散」を分けて書き直す必要がある。現実的な落とし所は、基盤の異なる選択肢を1つ確保する(ローカル実行モデル、あるいはBedrock/Vertex経由の別系統)か、AIが数時間止まっても業務が回る手順を明文化するかのどちらか。「両方やる」より「どちらかを決めて書いておく」方が実効性がある。もう1つは Claude Code v2.1.259 の `allowedMcpServers` 変更で、これまで許可リストで除外していたつもりの管理配布MCPサーバーがアップグレード後に有効化される。**意図せず権限が広がる方向の変更**なので、社内配布している環境があるならアップグレード前の棚卸しを優先タスクに置きたい。あわせて、管理設定ファイルがパースできないと起動そのものが止まるようになったため、配布中のJSON/plist/レジストリ値の検証も同時に行う。ベンチマークの読み方についても社内ルールを一つ足しておくとよい。GPT-6 Astra の件が示したのは、同じモデルでもハーネス次第でスコアが37ポイント動くということで、他社比較資料に数字を載せるなら測定条件の併記を必須にする。自社のモデル評価も、モデル差と文脈設計の差を分けて測る形にしておかないと、次に何を改善すべきかが読み取れない。
