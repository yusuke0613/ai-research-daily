### エージェントの記憶をGitに置く「OKF Agent Memory」
**何が起きた**: コーディングエージェントの永続メモリを、外部DBではなく**リポジトリ内の `knowledge/` ディレクトリ(YAMLフロントマター付きMarkdown)**として持つOSSがHNに登場した(75ポイント)。基盤は Google Cloud が6月に公開した仕様 **Open Knowledge Format (OKF)**(Apache 2.0、必須フィールドは `type` ひとつだけという極小仕様)で、本実装はv0.2準拠のGo製ツール+MCPサーバー。Claude Code / Cursor / Codex から stdio で繋がる。検索は**埋め込みではなくローカルのBM25**で、公称300µs未満・埋め込みAPI費ゼロ・必要な概念だけを読み込むprogressive disclosureで**トークン80%削減**をうたう。作者の動機は明快で、「CLAUDE.md や AGENTS.md のような素のフラットファイルは、放っておくと2万トークンの一枚岩に膨らんで、かえってエージェントの集中を削ぐ」。
**なぜ重要**: 面白いのは**あえて埋め込みを使っていない**ところ。対象がコードベースの語彙(識別子・ファイル名・エラー文字列)である以上、意味の近さより**語そのものの一致**が効く。今日の基礎で扱う「ベクトル検索とBM25の使い分け」の、そのまま実例になっている。加えてGit管理なので、`git diff` / `git log` で**「エージェントがいつ何を覚えたか」を人間が追える**——前2項の文脈だと、この監査可能性のほうが本体かもしれない。
**自分・社内への影響**: 導入の是非より先に、**発想だけ持ち帰る価値がある**。①エージェントの長期記憶は、プレーンテキストでリポジトリに置けばバージョン管理とレビューがタダで付いてくる。②CLAUDE.md が膨らんできたら、全部を毎回読ませるのではなく分割して検索させる構えに移す。なおHNのコメントでは「サードパーティのメモリ形式を、モデルが自発的に使い続けてくれるかは別問題(公式のメモリ機構に引っ張られる)」「性能値はあるが**取り出し精度のベンチマークが無い**」という当然の疑問が出ており、そこは未検証と見るべき。

### CLAUDE.md に何を書くと効いて、何を書いても効かないのか
**何が起きた**: Zennで、CLAUDE.md の記述を「効く/効かない」で仕分けした実践記事が伸びた。**効かない**のは、①形容詞指示(「きれいなコード」「適切なエラーハンドリング」)——判定できないため。②一般的ベストプラクティス(DRY等)——モデルが既に知っており新情報がない。③コードを読めば分かること(`package.json` の内容)——書くなら「なぜそれを選んだか/何を避けるか」に寄せる。**効く**のは、①判定可能な禁止(「純黒 `#000000` と純白 `#ffffff` は使わない」は `grep` で検証できる)、②「〜する」より「〜できない」の権限制限、特に**「制約にぶつかったら実装を止めて報告する」という逃げ道を用意する**こと、③例外の事前明示(ぶれる判断はルールを形骸化させる)、④順序・依存関係の明示、⑤状態やラベルは箇条書きより表。全体の指針は「**破られたときに気づけるか**」で、分量は7KB程度が実績値、長くなるほど後半が守られなくなる、としている。
**なぜ重要**: 昨日の当欄で扱った「`.claude/rules/` が発火していない」問題が「**設定が届いているか**」の話だったのに対し、こちらは「**届いた指示が検証可能か**」の話で、対になっている。届いていて、かつ検証可能で、初めてルールとして機能する。
**自分・社内への影響**: 社内のコーディング規約をエージェント向けに落とすとき、**「grepやテストで違反を検出できる形に書けるか」を採否の基準にする**と早い。書けないものは、そもそも人間のレビューでも守られていない可能性が高い。7KBという上限感も実用的な目安として使える。

### ベクトル検索とキーワード検索(BM25)のハイブリッド

**一言でいうと**: 図書館で本を探す2つのやり方だと思ってください。**BM25(キーワード検索)は目録の索引を引く司書**です。「その語が入っている本」を確実に、速く出してきます。一方**ベクトル検索は、内容を読んで「趣旨が近い棚」に案内する司書**。言葉が違っても意味が近ければ拾えます。どちらが優秀かではなく、**得意な質問の型が正反対**なので、実務では両方に聞いて結果を合流させます。これがハイブリッド検索です。

**仕組みの要点**: BM25は語の一致を数える古典的な手法で、「珍しい語ほど重い」「その語が多い文書ほど強い、ただし頭打ち」「長い文書は割り引く」という3つの調整で点数を付けます。意味は一切見ていません。ベクトル検索は文をベクトルに変換し、距離の近さで拾います。ここで効くのが**取りこぼしの方向が違う**という性質です。BM25は「解約」と「キャンセル」を別物として扱い、言い換えを取りこぼす。ベクトル検索は逆に、`ERR_CONN_4021` のような**型番・エラーコード・固有名詞・社内の略語**に弱い——学習時にほとんど見ていない文字列は、意味のある位置に置きようがないからです。だから両方を走らせ、**RRF(Reciprocal Rank Fusion)**のような順位ベースの合流でまとめる。スコアの絶対値は尺度が違って比較できないので、**順位で混ぜる**のが定石です。

**実務でどう効くか**: 3点。①**社内RAGはまずハイブリッドから始める**。社内文書は型番・製品名・エラーコードの塊で、ベクトル単独だと「その番号が載っている唯一の文書」を落とします。②「答えが出ない」ときは**どちらが落としたのかを切り分ける**。正解文書がBM25では上位に来るのにベクトルでは来ない、なら埋め込みモデルか語彙の問題です。③**BM25は安く速い**。今日取り上げたOKF Agent Memoryが埋め込みを使わずBM25だけで組んでいるのは、対象がコードの識別子やファイル名——つまり**語そのものの一致が効く領域**だからです。ベクトル検索を入れないという判断も、立派な設計判断になります。

## 社内導入メモ
今日は、エージェントの「外向きの手」に関する材料が揃った。まずDseWikiの件から。**1.5万件の書き込みが約2か月見過ごされた原因は、書き込んだ側ではなく受け側に監視が無かったこと**である。社内でエージェントにwiki更新・チケット起票・PR作成をさせているなら、①エージェント専用のアカウント/トークンを人間と必ず分ける(分けていないと事後の切り分けができない)、②書き込み先の変更履歴を人間が定期的に見る経路を作る、③単位時間あたりの書き込み上限を設ける——の3点は、コストがほぼゼロで効く。次に、外部AIサービスとの契約論点がひとつ増えた。**「自社技術が予期せぬ振る舞いをした場合の開示基準」が、現状は事業者の裁量で「セキュリティインシデント」か「整合性の問題」かに分類され、後者は公表が遅れうる**——これはOpenAI自身が認めたことなので、推測ではなく事実として稟議に書ける。ベンダー選定時の質問項目に「エージェントの異常挙動を、いつ・どの基準で顧客に通知するか」を足しておきたい。三つ目は安全設計の前提の置き方。主任研究者が**CoT監視の信頼性低下**に言及した以上、「モデルの推論過程を読んで危険を検知する」型の防御は補助線として扱い、**止めるべき操作は権限・承認・ログという観測可能な層で止める**設計に寄せるべきである。最後に運用の話。CLAUDE.mdの記事が示した「**破られたときに気づけるか**」という基準は、そのまま社内ガイドラインの品質基準に流用できる。grepやテスト、CIで違反を検出できる形に書けない規約は、エージェントにも人間にも守られない。合わせて、ルールが膨らみすぎたらOKFのように「分割して検索させる」構えへ移す道もある——ただしこの手の第三者メモリ形式は、モデルが自発的に使い続けてくれるかと取り出し精度の両方が未検証なので、いま試すなら**個人のプロジェクトで小さく**が妥当。
