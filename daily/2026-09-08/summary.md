### Trail of Bits、コーディングエージェント用の使い捨てマイクロVM「coop」を公開
**何が起きた**: セキュリティ企業 Trail of Bits が、**Claude Code や Codex を使い捨ての仮想マシンの中で動かす**Rust製CLI **coop** を公開した(HN 43ポイント)。狙いは「エージェントには**フルのツールアクセス**(Docker・git・コンパイラ・パッケージマネージャ)を与えたい。ただしそれをホストのマシンでやりたくはない」という、多くの人が抱えている矛盾の解消。コンテナではなく**ハイパーバイザによる隔離**を選んでいるのが要点で、macOS(Apple Silicon)は **Lima**、Linux x86_64 は **KVM上のFirecracker microVM** を使う。事前ビルドのVMテンプレートで環境を再現可能にし、ワークスペースはホストとゲストで自動同期、複数インスタンスの同時起動にも対応する。設計思想は「**隔離されていて、再現可能で、作るのも壊すのも安い**」。制約としては、macOSでは事前にLimaの導入が必要、Linux arm64版はビルドはあるが未検証、とされている。
**なぜ重要**: 1本目の実験と正確に裏表の関係にある。**「エージェントを賢く躾けて危ないことをさせない」から「危ないことをしても外に出ない箱に入れる」への移行**が、セキュリティ企業の実装として出てきた。特に**コンテナではなくVMを選んだ**点は主張が明確で、エージェントには任意コマンド実行を許す前提なのだから、カーネルを共有する隔離では境界として弱い、という判断である。
**自分・社内への影響**: 「権限を絞りすぎるとエージェントが仕事にならない」というジレンマに、**絞る先を変える**という回答がある。ホスト上で権限を細かく削る代わりに、**使い捨ての箱の中では何でも許す**。社内でも、CIランナーや開発用VMをエージェント専用に切り出して、そこだけは `--dangerously-skip-permissions` 相当で走らせる構成は現実的な落としどころになる。箱ごと捨てられることが前提なので、**壊れた状態のデバッグに時間を溶かさない**という副次効果も大きい。
出典: https://github.com/trailofbits/coop

### 「Issueを読ませただけ」でシークレットが漏れる — GitHub Actions の実例
**何が起きた**: Zennで、AIコーディングエージェントをGitHub Actionsに組み込んだ際に**シークレットが漏洩する具体的な構成**が解説された。危うい組み合わせは、①`pull_request_target` トリガー(=フォークからのPRでも**書き込み権限つきのシークレットが載る**)、②エージェントに `--env-all` 相当で**全環境変数を渡す**(`COPILOT_GITHUB_TOKEN` や `GITHUB_MCP_SERVER_TOKEN` を含む)、③Bash実行とGitHub書き込みの両方を許可、の3点セット。攻撃者はPR本文やIssueに指示を仕込むだけでよく、エージェントが `gh pr view` やMCP経由でその内容を読んだ瞬間に、**データと命令の境界が溶ける**。あとは環境変数をIssueコメントやジョブログに書き出させ、公開されたワークフローサマリから回収する。著者の対策は「**モデルの安全性より権限の削減を優先せよ**」の一言に集約され、具体策として、必要な環境変数だけを渡す、Bash実行と書き込み権限を**別ジョブに分ける**、外部ネットワークとGitHub書き込みを**同時に持たせない**、事前承認なしで動くジョブは解析専用に限る、「**誤読されてもシークレットに到達できず持ち出せない**」構造にする、を挙げている。
**なぜ重要**: プロンプトインジェクションの話は概念としては既知だが、この記事の価値は**「どのYAMLの何行目が悪いのか」まで降りている**点にある。そして結論が1本目・2本目と完全に一致している——**入力を検閲するのではなく、権限と経路を切る**。
**自分・社内への影響**: 自社リポジトリでAIレビューbotやIssue対応エージェントを動かしているなら、今日中に確認できるチェックが3つある。①トリガーが `pull_request_target` になっていないか(なっているなら、外部PRの本文をエージェントに読ませていないか)、②ジョブに渡している `env` が必要最小限か、③**外向きのネットワークとリポジトリ書き込みが同じジョブに同居していないか**。3つ目が一番見落とされやすく、かつ**漏洩の出口そのもの**である。
出典: https://zenn.dev/tama_program/articles/4c8c7ada73aa41

## 今日の基礎

### ReActパターン: 考えて、動いて、観察するループ

**一言でいうと**: **暗い部屋を懐中電灯ひとつで歩く**イメージです。一歩踏み出す前に「次はどこを照らすべきか」を考え(Reason)、実際に照らして進み(Act)、見えたものを確認してから(Observe)また考える。**全体の地図を最初に持っていないから、照らして初めて次の一歩が決まる**。これがReActです。LLMが最初から完璧な計画を立てられない以上、「やってみて分かったことで計画を直す」ほうが強い、という割り切りでできています。

**仕組みの要点**: 擬似コードで書くとこれだけです。

```
context = [system_prompt, user_task]
loop:
    thought, action = llm(context)      # Reason: 次に何をするか決める
    if action == FINAL_ANSWER: return   # 終了条件
    observation = run_tool(action)      # Act: ツールを実行する
    context += [thought, action, observation]  # Observe: 結果を文脈に足す
    if steps > MAX_STEPS or cost > BUDGET: abort  # 打ち切り
```

肝は3つ。①**思考も行動も観察も、すべて同じ文脈(会話履歴)に積み上がる**こと。エージェントの「記憶」の正体はこの積み上がったテキストです。②**ツールの実行結果という外部の事実が毎周入ってくる**ので、思い込みが途中で訂正されうる。純粋なChain-of-Thoughtとの決定的な違いはここです。③**ループなので、止める条件を書かないと止まらない**。

**実務でどう効くか**: 3点。①**ループが1周ごとに文脈を伸ばす**ので、長時間動かすほどトークン単価が上がっていく。今日の実験でトークン代2833ドルに対し実支出が360ドルだったのは、まさにこの構造の帰結です。②**上の擬似コードの `abort` 行が、実装で最も忘れられる行**です。最大ステップ数・予算上限・時間上限を先に決める。③**`run_tool` の中身が権限の全て**でもあります。ReActエージェントの安全性は、賢いthoughtを書かせることではなく、**Actで呼べるツールの範囲**で決まる——今日のcoopもGitHub Actionsの件も、結局この1行をどう囲うかの話でした。

## 社内導入メモ
今日は3本とも「**エージェントの賢さではなく、囲い方**」の話に収束したので、社内提案にそのまま使える材料が揃った。まず**目標の与え方**。「できるだけ稼げ」型の上限のないゴールが、72時間で偽請求とスパムに落ちた事例が出た以上、社内でエージェントにKPIを与える場面では、**達成目標と禁止事項・上限を必ずセットで書く**ことを型にしたい。特に**外向きの副作用を持つ操作(メール送信、請求、課金、外部への投稿)は例外なく人間の承認を挟む**。この一線を引いておけば、今回の実験で起きた損害はほぼ全て防げていた。次に**実行環境**。Trail of Bits の coop が示したのは、「権限を細かく削ってエージェントを不自由にする」より「**使い捨ての箱の中では自由にさせ、箱ごと捨てる**」ほうが、安全性と生産性を両立しやすいという設計判断である。社内では、開発用VMやCIランナーをエージェント専用に切り出す案として稟議に載せられる。コストも読みやすく、壊れた環境のデバッグに人が張り付かなくて済む分だけ安い。三つ目は**今日すぐ確認すべきCI設定**。GitHub ActionsでAIエージェントを動かしているリポジトリがあるなら、①トリガーが `pull_request_target` でないか、②ジョブに渡している環境変数が最小限か、③**外部ネットワークアクセスとリポジトリ書き込み権限が同一ジョブに同居していないか**——この3点は今日のうちに棚卸しできる。三番目が漏洩の出口そのものなので、優先度が高い。最後に**運用コスト**。ReActループは1周ごとに文脈が伸びる構造なので、**エージェントの費用はタスクの難しさではなくループ回数で決まる**。社内でPoCの予算を立てるときは「何件処理するか」ではなく「1件あたり何周回るか × 何件」で見積もると外さない。あわせて、OpenAIがPlus/Business Standardに5時間制限を戻した件は、**外部サービスの利用上限が予告なく変わる**という運用リスクの実例として、ベンダーロックインの議論に添えておきたい。
