### Anthropic、Claude Fable 5.1 と Mythos 5.1 を公開
**何が起きた**: 同一の基盤モデルを2つの形で提供する構成。Fable 5.1 は通常のセーフガード付きで全プラットフォーム(Claude.ai / Claude API / AWS / Google Cloud / Azure)に即日提供、API識別子は `claude-fable-5-1`。Mythos 5.1 は同じモデルをセーフガードを緩めた形で提供するもので、米国組織向けの2つの審査付きプログラム(Cyber Verification Program、Life Sciences Verification Program)経由に限定される。価格は入力$10/出力$50 per Mtok、キャッシュ読み出しは$0.25 per Mtok(従来比75%減)で、典型的な用途で Fable 5 比およそ25%、エージェント的な用途では最大45%安くなるとしている。ベンチマークは Terminal-Bench 4.0 が Fable 5.1 で55.8%(Mythos 5.1 は60.9%)、Terminal-Bench-Science 0.1 が52.6%(Fable 5 は24.7%)、Humanity's Last Exam が60.9%(ツールなし)/65.0%(ツールあり)、OSWorld 2.0 が41.7%(strict)。科学分野では、既存の競技優勝作より10倍高い親和性のタンパク質バインダー設計や、30年前のNASAレーダーデータからの金星標高マップの解像度向上(10〜20km→2〜3km)といった事例が挙げられている。誤検知の削減(サイバー系タスクで60%減、良性の生物・医療系質問で85%減)、EU AI Act対応の透かし、蒸留対策の強化も含まれる。
**なぜ重要**: 「能力の高いモデルを危険用途と切り離す」問題に対して、モデルを分けるのではなく**同じモデルにセーフガードの強度差を持たせ、緩い方を審査付きの窓口に閉じる**という設計を出してきた点が新しい。誤検知削減の数字が前面に出ているのも、実務で最も摩擦になっていたのがそこだったことの裏返し。
**自分・社内への影響**: 価格改定で効くのはキャッシュ読み出しの$0.25。長いシステムプロンプトや固定のコンテキストを毎回送る構成ほど恩恵が大きいので、既存の見積もりはキャッシュヒット率を前提に引き直す価値がある。

### Google、Gemini APIに「エージェント型動画理解」を追加
**何が起きた**: これまで動画は一定フレームレートで頭から末尾まで処理していたが、新機能ではモデル自身が「どこを、どの速度で、どのチャネル(フレーム/音声/文字起こし)で見るか」を判断し、必要な区間だけをツール経由で取りに行く。必要なら同じ場面を高フレームレートで見直す。Google公表値でトークン最大88%減、コスト最大66%減、精度は最大7%向上。長尺動画のベンチマークでは1クエリあたり30〜40万トークンが5万トークン未満に落ちたとされる。対象は Gemini 3.7 Flash / 3.6 Flash / 3.5 Flash-Lite で、Google AI Studio と Gemini Enterprise Agent Platform から利用可能。Geminiアプリと YouTube の「Ask YouTube」への展開も予告されている。
**なぜ重要**: 「全部を文脈に入れる」から「必要な部分をエージェントが取りに行く」への移行が、テキストのRAGだけでなく動画にも降りてきた形。ロングコンテキストの安さ勝負ではなく、取りに行く回数で勝負する設計が主流になりつつある。
**自分・社内への影響**: 議事録動画・研修動画・監視映像のような長尺素材を扱っているなら、まずここを試す価値が高い。既存コードからの移行コストは小さい一方、コスト構造が桁で変わる領域。
出典: https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-agentic-video-in-gemini/

### Claude Code v2.1.257、Auto Modeに「Containment Escape」ルール
**何が起きた**: 変更履歴に「クラウドのメタデータ認証情報の取得、egress回避、クロステナントへの到達は、環境側で想定内と明示していない限り自動承認しない」というルールの追加が入った。あわせて、Auto Mode で作業ディレクトリ外のファイルを初めて読む前に一度だけ確認を出す挙動と、それ自体を禁止する設定 `permissions.blockReadsOutsideWorkingDirectories` が追加されている。既定モデルは Claude Fable 5.1(1Mコンテキスト)に。権限まわりの修正も多く、`permissions.ask` ルールが複合コマンドやサブシェル内で素通りしていた問題、Bash の `Read()`/`Edit()` 拒否ルールが `< file` リダイレクトや `tac`・`egrep` に効いていなかった問題、プラグインがシンボリックリンク経由で自ディレクトリ外を読めた問題が直された。
**なぜ重要**: 昨日取り上げた Auto Mode への間接プロンプトインジェクション報告に対し、Anthropicは「本当の防御境界はOS隔離とegress制御」と回答していた。今回の変更は、その境界に触る動作(認証情報の取得・外向き通信の抜け道)を**自動承認の対象から外す**という形で、エージェント側にも一段の網をかけたことになる。防御の主役をエージェント外側に置く方針自体は変わっていない点に注意。
**自分・社内への影響**: 自動実行を回している環境では、更新後に想定内の操作まで確認を求められる可能性がある。止まる箇所を洗い出して環境側で「想定内」と明示する作業が要る。複合コマンド内で `permissions.ask` が素通りしていた件は、これまでの権限設定が想定通りに効いていなかった可能性を意味するので、無人運用しているなら早めに更新したい。
出典: https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md

### Anthropic、Enterprise Frontier Safeguards を発表
**何が起きた**: 「データを外部に預けたくない規制業種」と「悪用検知にはセッションを跨いだ履歴分析が必要」という相反する要求を両立させる仕組み。利用状況のデータは顧客自身のクラウド(S3 / Azure Blob / GCS)に、顧客の鍵で保管される。Anthropic側のシステムは自動的なパターン検知(サイバー攻撃、盗用された認証情報、違法な能力開発など)のみを行い、アラートを顧客に直接送る。Anthropicの人間がデータを閲覧することはなく、確認と判断は顧客のセキュリティチームが行う。Claude 直接契約に加え Amazon Bedrock / Google Cloud / Azure でも利用でき、100社超(Goldman Sachs、Morgan Stanley、Citi、Salesforce、Stripe、Snowflake など)と共同開発された。追加料金は無く、クラウドの保管費用のみ発生する。
**なぜ重要**: ゼロデータ保持と悪用検知はこれまでトレードオフとして扱われてきたが、「保管場所を顧客側に置き、検知だけをベンダーが行う」という分割で両立させている。規制業種のAI導入で最後に残る論点への具体的な解答になっている。
**自分・社内への影響**: 情報システム部門とのゼロデータ保持交渉で「じゃあ悪用検知はどうするのか」に詰まっていた場合、この構成が交渉のたたき台になる。
出典: https://www.anthropic.com/news/enterprise-frontier-safeguards

### チャンク分割: 文書をどう切るかが精度の半分を決める

**一言でいうと**: チャンク分割は、本を検索できるようにするために**付箋を貼る作業**です。付箋を1ページごとに貼れば細かく引けますが、話が途中で切れて意味が通じません。章ごとに貼れば文脈は保てますが、大きすぎて「この章のどこ?」となる。どの粒度で貼るかがRAGの検索精度をほぼ決めてしまいます。

**仕組みの要点**: RAGは文書をチャンクに切り、それぞれを埋め込みベクトルにして保存します。検索でヒットする単位も、LLMに渡される単位も、このチャンクです。つまり**切り方が悪ければ、後段でどれだけ良いモデルを使っても答えは出ません**。代表的な3つの切り方を押さえます。①**固定長チャンク**は文字数やトークン数で機械的に切る方式(例: 500トークンごと、前後50トークンをオーバーラップ)。実装が最も簡単で、どんな文書にも使えますが、文や表の途中で切れる事故が起きます。オーバーラップは、境界で切れた情報を隣のチャンクが拾えるようにする保険です。②**意味単位チャンク**は見出し・段落・箇条書きなど文書の構造に沿って切る方式。MarkdownやHTMLのように構造が明示された文書では第一選択で、1チャンク=1つの話題になるため検索の精度が上がります。③**階層チャンク**は「章の要約」と「節の本文」のように大小2層以上を持たせ、小さい単位で検索して大きい単位を返す(あるいは親の見出しを子チャンクに付与する)方式です。「この規程の第3条は?」のような局所的な質問と「この規程は何を定めているか」のような俯瞰的な質問を、同じインデックスで両立させられます。

**実務でどう効くか**: 社内文書なら、まず**構造で切れるか**を確認するのが早道です。見出しが機能している規程やマニュアルなら意味単位、構造が壊れているPDFのスキャンなら固定長+オーバーラップから始める。判断に迷ったら、検索結果として返ってきたチャンクを人間が読んで「これだけで質問に答えられるか」を確かめてください。答えられないなら、モデルを変える前にチャンクを見直す番です。よくある失敗は、表を行の途中で切ってヘッダを失う、Q&A文書で質問と回答が別チャンクに分かれる、チャンクにファイル名や章タイトルを付けていないためLLMが出典を言えない、の3つ。いずれも切り方の設計で防げます。

## 社内導入メモ
今日は「規制業種でのAI導入の最後の壁」に効く材料が出た。Enterprise Frontier Safeguards が示したのは、ゼロデータ保持と悪用検知は二者択一ではなく、**保管場所と検知主体を分ければ両立する**という設計だ。情報システム部門との議論が「ログを外部に出せない」で止まっている場合、この構成——活動データは自社のS3/Blob/GCSに自社の鍵で置き、ベンダー側は自動検知とアラート送信だけを行い、閲覧と判断は自社セキュリティチーム——をそのまま論点整理に使える。追加料金が無く、Bedrock / Google Cloud / Azure 経由でも使える点も、既存のクラウド契約を活かせるので通しやすい。あわせて Claude Code v2.1.257 の Containment Escape ルールは、昨日整理した「防御はエージェントの外側に置く」という原則と矛盾しない範囲での内側の補強として位置づけたい。社内ガイドラインに書くなら「エージェント製品側の自動承認ルールは補助であって境界ではない」と明記したうえで、コンテナ/VM実行・egress許可リスト・実行環境から本番認証情報を外す、の3点を必須要件として残す形が妥当。今回の更新で自動実行が想定外の箇所で止まる可能性があるため、無人運用しているRoutineは更新後に一度、通しで動くかを確認する運用を入れておきたい。
