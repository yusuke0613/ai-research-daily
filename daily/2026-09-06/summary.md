### Claude Code の Rules が8月18日頃から発火していない、という報告
**何が起きた**: 9月5日、kawasin73氏がブログで、`.claude/rules/` に置いたパス指定つきのルールがファイル編集時に発火していないことに気づき、Claude Codeのバイナリを逆引きして原因を特定したと報告した。指摘によれば、Claude Codeが `Read` ツールではなく `cat`/`sed`/`grep` などのBashコマンドでファイルを読むようになった結果、**`Read` に紐づいて発火する仕組みが軒並み動かなくなっている**。影響はRulesだけでなく、**Readツールで発火するHooks**と**サブディレクトリに置いた CLAUDE.md の読み込み**にも及ぶという。回避策として `.claude/settings.json` で環境変数 `CLAUDE_CODE_THRIFTY_SONIC` を `false` にする方法が挙げられている(この変数は公式ドキュメントに記載がなく、GitHub issue内で言及されているのみ)。はてなブックマークは232users。
**なぜ重要**: 設定ファイルを置いたこと自体は、それが読まれている証拠にならない——という話が、昨日の権限ルールの穴(v2.1.260の修正)に続いて2日連続で出ている。しかも今回は**エラーも警告も出ない**種類の不発で、気づく手がかりがない。
**自分・社内への影響**: `.claude/rules/` や Read系Hooks、モノレポでサブディレクトリごとに CLAUDE.md を置く構成に依存しているなら、まず「本当に読まれているか」を1回確かめたい。確認方法は単純で、ルールに「この指示を読んだら冒頭に決まった一言を出力する」といったカナリアを1行入れて、対象ファイルを編集させてみればよい。出なければ効いていない。なおこれは第三者による観測とバイナリ解析の報告であり、Anthropicの公式アナウンスではない点に注意。

### Chrome V8 のゼロデイ CVE-2026-85046 が実環境で悪用中
**何が起きた**: Googleが、V8の型混同(CWE-843)脆弱性 **CVE-2026-85046** の修正版を配布開始した。細工したHTMLページを開かせるだけでサンドボックス内で任意コード実行が可能で、**Googleは実環境での悪用を確認している**。CVSSは8.8、修正版は Windows/macOS が 152.0.7977.82/.83、Linuxが 152.0.7977.82。2026年に入って6件目のChromeゼロデイ。発見者は研究者 Salvatore Gulizia 氏(8月4日報告)で、報奨金は $1,000。HNでは720ポイント・414コメントを集め、議論の中心はこの報奨金額の妥当性だった。
**なぜ重要**: V8はChromeだけのものではない。**Electron製のデスクトップアプリ**(AIチャットクライアントやIDE系ツールを含む)と、**ヘッドレスChromiumでウェブを見に行くエージェント**が同じエンジンを共有している。しかも後者は、人間なら開かないページを自動で開きに行く。攻撃者から見れば「怪しいURLを踏ませる」工程が省ける相手になる。
**自分・社内への影響**: 対応は3点。①Chrome/Edge/Braveを152.0.7977.82以降に上げる(社内配布なら強制更新)。②PlaywrightやPuppeteerでブラウザを動かしているエージェント基盤は、同梱Chromiumのバージョンを確認して更新する——ここは自動更新が効かないので取り残されやすい。③Electron製アプリはアップストリーム取り込み待ちになるため、更新が出るまでの間、未知のリンクを自動で開かせる運用を止める。

### 「Portal by Spotify でClaude Codeのトークンが90%減った」とHNの冷めた反応
**何が起きた**: 9月4日、Spotifyのエンジニアリングブログが「Portal by Spotify cut my Claude Code token usage by 90%」を公開。Portalは同社のBackstage系の開発者ポータルで、プラグインの機能を**MCPツールとして公開**し、Claude Code / Cursor / VS Code Copilot などのエージェントから発見・利用できる。鍵になっているのが **modes** で、指示・モデル・temperature・接続するMCPツールを宣言的に定義し、エフェメラルなランタイムで動かす小さなエージェント。要するに「フロンティアモデルのトークンを、フロンティアモデルでなくてよい仕事に燃やさない」構成である。HNは239ポイント・145コメント。
**なぜ重要**: 反応がほぼ一様に懐疑的だったのが本題。「要は賢くないモデルに投げているだけでは」「Claude Codeはもともと大きなコードベースの読み込みをHaikuサブエージェントに委譲している」「**精度や性能の話が一切ない。せめてSWE系ベンチで測ってほしい**」——90%という数字は削減側しか見ていない、という指摘である。「自分でコードを書いてトークン消費を100%削減した」という皮肉もあった。
**自分・社内への影響**: 発想自体(社内ツール群をMCPで束ね、定型作業は安いモデルの専用エージェントに固定する)は素直に有効で、社内ポータルを持っているなら検討に値する。ただし持ち帰るべき教訓は逆側にある——**コスト削減の施策は、削減率と一緒に品質指標を出さないと評価できない**。社内で同種の提案をするなら、削減率・失敗率・やり直し回数の3つを最初からセットで測る設計にしておきたい。やり直しが増えれば削減分は消える。
出典: https://engineering.atspotify.com/2026/9/portal-by-spotify-cut-my-claude-code-token-usage-by-90 , https://news.ycombinator.com/item?id=49571465 , https://backstage.spotify.com/docs/portal/core-features-and-plugins/mcp/overview

### コンテキストウィンドウ: モデルの「作業机の広さ」

**一言でいうと**: コンテキストウィンドウは、モデルの**作業机の広さ**です。引き出し(=学習済みの知識)とは別物で、机の上に広げた資料だけを見ながら答えを書きます。机に載らなかった資料は、存在しないのと同じ。そして机は毎回まっさらで、前回広げた紙は残っていません。「さっき言ったよね」が通じないのは、記憶力の問題ではなく机の仕様です。

**仕組みの要点**: 会話が続くたびに、システムプロンプト・過去のやり取り・ツールの実行結果を**全部まとめて毎回投げ直して**います。長い会話ほど遅く高くなるのはこのため。上限を超えると、古い部分が捨てられるか要約に置き換わります(Claude Codeの自動コンパクトがこれ)。ここで重要なのが、**机は広ければ広いほど良い、とはならない**点です。入力が長くなるほど、真ん中に置いた情報の参照精度が落ちる傾向が繰り返し報告されていて、**lost in the middle** と呼ばれます。仕組み上、モデルは全トークンに一様な注意を払うわけではなく、冒頭と末尾が相対的に強く効きます。100万トークン入るモデルでも、100万トークン詰めれば100万トークン分きちんと読む、という保証はありません。

**実務でどう効くか**: 3つ。①**大事な指示は末尾に**置く。長い資料を貼った後に「で、何をしてほしいか」を書くほうが通ります。②**入れる前に削る**。ログやコマンド出力を丸ごと貼るより、必要な数十行に絞ったほうが精度が上がります(長いほど賢くなる、ではない)。③**長い一本の会話より、短いセッションを複数**。タスクが切り替わったら新しい会話を始めるほうが、机が散らかっていない分だけ精度が出ます。今日のPortalの話——重い読み込みを安いモデルの小さなエージェントに切り出す構成——も、コスト削減と同時に「机を散らかさない」ための設計として読めます。

## 社内導入メモ
今日は即応が要る材料が1つと、提案書向けが2つ。まず即応。Chrome V8のゼロデイ(CVE-2026-85046)は実環境で悪用が確認されているので、①ブラウザの強制更新に加えて、②**エージェント基盤が同梱しているChromiumの更新**を忘れないこと。Playwright/Puppeteerを使った社内の自動化やスクレイピング基盤は、OSやブラウザの自動更新の外側にいるため取り残されやすく、しかもエージェントは人間が開かないURLを自動で開きに行く分だけ被弾面が広い。③Electron製のAIクライアントは修正の取り込みに時間差があるので、その間だけでも未知のリンクを自動で開かせる運用は止めておきたい。次に提案書向け。Claude CodeのRules不発の件は、「ルールを設定した」ことと「ルールが効いている」ことが別だという、昨日の権限ルールの穴に続く2例目になった。ガイドラインを配って終わりにせず、**設定が効いていることを確認する手順**を運用に入れる必要がある——具体的には、ルールにカナリア(読まれたら決まった一言を出す指示)を仕込んで定期的に確認する、Hooksは実行ログを残す、という2点。エージェントは失敗を黙って握りつぶすのではなく、設定が効いていないことを人間に見せない形で動き続ける点が厄介である。最後にモデル選定。総合ベンチの順位で社内標準を決める運びになりがちだが、Artificial Analysisの件が示したとおり、指標そのものが結果を見てから変わりうる。自社の代表タスク20〜50件と合否基準を用意しておけば、モデルが入れ替わるたびの再評価が数時間で終わり、稟議の根拠も「外部ランキング1位」より強くなる。GoogleのFairwindは自社では使えないが、「テストで正しさを判定できる領域(脆弱性修正・型検査・スキーマ検証)から先にエージェントを入れる」という優先順位づけの外部事例として引用できる。
